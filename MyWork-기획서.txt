# MyWork — 개인 업무 관리 대시보드 기획서

- 문서 목적: 기존에 운영 중인 MyWork 시스템의 전체 기능을 새로운 환경에서 재구축하기 위한 요구사항 정의
- 작성일: 2026-07-31
- 대상 사용자: 단일 사용자(개인 업무 관리), 로컬 환경 실행
- 비고: 본 문서는 현재 운영 중인 시스템의 확정 사양이다. "선택 사항"이라고 명시하지 않은 모든 항목은 필수 구현 대상이다.


## 1. 서비스 개요

개인의 업무(태스크)를 등록·관리하고 요약/목록/칸반보드/캘린더/타임라인 5가지 뷰로 시각화하는 업무 대시보드.
데이터는 로컬 DB에 영구 저장하며, 웹 UI 외에 AI 에이전트(Claude Code)가 MCP(Model Context Protocol) 서버를 통해
동일 데이터를 조회·수정할 수 있어야 한다.

핵심 원칙:
- 검증 규칙(입력 검증·비즈니스 규칙)은 단일 모듈에 한 곳에만 존재하고, 웹 API와 MCP 양쪽이 이를 공유한다.
  어느 경로로 들어와도 같은 규칙을 통과해야 한다.
- 단일 사용자용이므로 로그인/권한 기능은 없다.


## 2. 용어 정의

| 용어 | 정의 |
|------|------|
| 태스크 | 업무 1건. 제목·유형·진행상황·업무분류·우선순위·시작일·마감일·메모·반복주기·보관여부·상위태스크를 가진다 |
| 체크리스트 | 태스크 내부의 세부 항목 목록. 각 항목은 제목·완료여부·정렬순서를 가진다 |
| 하위 태스크 | 태스크끼리의 상하위 연결. 하위도 독립된 태스크로서 자기 상태·마감일·체크리스트를 가진다 (체크리스트와 별개 개념) |
| 설정 항목 | 업무유형·진행상황·우선순위·업무분류 4종. 모두 사용자가 추가·수정·삭제·순서변경 가능한 데이터이며 하드코딩하지 않는다 |
| done 플래그 | 진행상황 항목 중 "끝남"을 뜻하는 상태 표시. 이름('완료' 등)이 아니라 이 플래그가 완료 판정의 유일한 기준 |
| 보관(archive) | 완료 태스크를 모든 뷰·통계에서 제외하는 소프트 삭제. 복원 가능 |


## 3. 화면 구성

화면은 현행 시스템과 **동일하게** 재현한다. 구체적 색상·치수·타이포그래피는 「부록 A. 화면 디자인 상세 명세」를 따른다.

### 3.1 공통 레이아웃

- 상단 헤더: 뷰 전환 내비게이션(요약·목록·보드·캘린더·타임라인), 검색창, 필터, [완료 숨김] 토글, [설정] 버튼, [정리] 버튼, [새 태스크] 버튼
- 사이드바: 업무분류 목록(분류별 색상 점 표시). 분류 클릭으로 해당 분류만 표시/해제 토글
- 5개 뷰는 각각 독립된 페이지(별도 HTML)로 물리 분리한다. 공통 로직(상태 관리·API 호출·모달)은 공용 스크립트로 공유한다.

### 3.2 요약 뷰

- 통계 카드 4종: 전체 / 진행 중 / 완료 / 지연 건수
- 업무분류별 진행 스택바: 분류마다 상태 분포를 가로 막대로 표시, 우측에 체크리스트 반영 진척률(%) 표시
  (막대 = 상태 분포, 진척 % = 체크리스트 반영값으로 서로 다른 수치임)
- 업무유형 분포 차트
- 마감 임박·지연 태스크 목록
- [완료 숨김] 토글의 영향을 받지 않는다 (완료 건수·진척률을 보여야 하므로)

### 3.3 목록 뷰

- 전체 태스크 테이블. 모든 컬럼 헤더 클릭으로 정렬 가능
- 행 클릭 시 수정 모달, 행 우측 × 버튼으로 인라인 삭제(확인 절차 없음)
- 제목 아래 체크리스트 진행률 배지(예: 2/5), 반복 배지(🔁 2주마다) 표시
- 하위 태스크는 상위 바로 아래에 들여쓰기로 붙여 표시. 상위가 필터로 안 보이면 하위는 제자리에 남는다
- 상위 태스크에는 하위 완료 현황 배지(⑂ 1/3, 무채색) 표시

### 3.4 보드 뷰 (칸반)

- 진행상황별 열(column). 열 순서 = 진행상황 설정의 순서
- 카드를 드래그해 다른 열에 놓으면 진행상황 변경
- 열 머리의 핸들(⠿)을 드래그하면 열 순서 변경. 이는 진행상황 설정의 순서 값 자체를 바꾼다(설정 화면과 동일 데이터)
- 카드: 제목, 분류 태그(분류 색), 마감일, 체크리스트 진행 바, 반복 배지
- 하위 태스크 카드: 왼쪽 세로선 + "↳ 상위 제목" 칩(클릭 시 상위 태스크 모달 열림). 상위 카드에는 ⑂ 태그
- [완료 숨김] 상태에서도 done 열은 드롭 대상으로 유지되어 드래그로 완료 처리 가능

### 3.5 캘린더 뷰

- 마감일 기준 월간 달력. 태스크를 해당 마감일 칸에 표시(분류/유형 색 반영)

### 3.6 타임라인 뷰

- 간트 차트. 시작일~마감일을 가로 막대로 표시, 오늘 기준선 표시

### 3.7 공통 필터·검색

- 검색: 제목·메모 대상
- 필터: 업무분류·업무유형·우선순위
- [완료 숨김] 토글: done 상태 태스크를 숨긴다. 목록·보드·캘린더·타임라인에만 적용, 요약 뷰 제외.
  토글 상태는 저장하지 않는다(새로고침 시 해제) — 일시적 시야 정리 용도

### 3.8 태스크 모달 (생성·수정 공용)

- 필드: 제목, 업무유형, 진행상황, 업무분류, 우선순위, 시작일, 마감일, 메모, 반복 주기, 상위 태스크
- 하단 체크리스트 영역: 항목 추가·체크·삭제·드래그 순서변경 — 모두 즉시 저장.
  나머지 필드는 [저장] 버튼을 눌러야 반영 (신규 태스크는 저장 후에만 체크리스트 추가 가능)
- 체크리스트 드래그 시 끄는 방향에 따라 목표 항목 위/아래에 삽입선 표시, 놓으면 서버가 전체 순서를 0..n-1로 재부여
- 상위 태스크 필드: 하위를 가진 태스크에는 이 필드 대신 안내 문구 표시(하위를 가진 태스크는 남의 하위가 될 수 없으므로)
- 하위 태스크 목록(상위 태스크의 모달 하단): 하위 클릭 시 해당 태스크 모달로 전환.
  [+ 하위 태스크 추가]는 열려 있던 수정 내용을 먼저 저장한 뒤, 상위의 분류·유형·마감일을 물려받은 새 태스크 모달을 연다

### 3.9 설정 모달

- 업무유형 · 진행상황 · 우선순위 · 업무분류 4종을 동일한 UI·동일한 규칙으로 관리
- 각 항목: 이름, 색상, (진행상황만) done 플래그
- 조작: 추가 / 이름 변경 / 색상 변경 / 삭제 / 드래그 순서 변경
- 칩 배경색은 지정 색의 10% 투명도로 자동 계산(색을 두 번 고르지 않는다)

### 3.10 정리(보관) 모달

- 기준일 선택(기본: 30일 전) → 해당 날짜 이전에 마감된 done 태스크 건수를 먼저 보여주고, 확인 후에만 일괄 보관
- 모달 하단에 보관된 태스크 목록: 개별 [복원], [영구 삭제] 버튼


## 4. 기능 요구사항 (비즈니스 규칙)

### 4.1 태스크

- 생성 시 전 필드 필수(메모 제외). 서버 측 검증:
  - 유형·진행상황·우선순위·분류는 설정 항목 화이트리스트 검사
  - 날짜는 YYYY-MM-DD 형식
  - 시작일 > 마감일이면 거부(400)
- 부분 수정(PATCH) 지원 — 모달 저장과 보드 드래그 상태 변경이 같은 엔드포인트 사용
- 삭제 시 체크리스트는 함께 삭제(CASCADE), 하위 태스크는 연결만 해제(아래 4.3)

### 4.2 체크리스트

- 태스크당 0..n개. 체크·추가·삭제·순서변경 즉시 저장
- 진행률(체크됨/전체)을 목록 뷰 배지와 보드 카드 진행 바에 표시
- 항목을 모두 체크해도 태스크 상태는 자동으로 바뀌지 않는다 — 상태 전환은 항상 수동

### 4.3 하위 태스크 (상하위 연결)

- 깊이 1단계 제한(Jira 방식): 하위에 다시 하위를 붙일 수 없고, 하위를 가진 태스크는 다른 태스크의 하위가 될 수 없다.
  이 규칙으로 자기참조·순환이 원천 차단된다. 위반·자기참조·존재하지 않는 상위 지정은 400
- parent_id로 생성·수정 양쪽에서 지정, null이면 연결 해제
- 상위 삭제 시 하위는 지워지지 않고 연결만 끊겨 최상위 태스크가 된다(ON DELETE SET NULL).
  삭제 버튼에 확인 절차가 없으므로 CASCADE는 금지
- 하위 태스크 표시 색은 상위의 업무분류 색을 상속(CSS 변수). 상하위 전용 색을 고정하지 않는다
  — 유형·분류 색이 모두 사용자 설정값이라 어떤 고정색도 언젠가 충돌하기 때문.
  "하위다"라는 사실은 형태(세로선·↳ 칩·들여쓰기)로, 색은 "누구의 하위인가"만 전달
- 하위의 완료 여부는 상위 진척률에 반영하지 않는다. 진척률은 체크리스트 기준 유지

### 4.4 설정 항목 관리 (4종 공통 규칙)

- 업무유형·진행상황·우선순위·업무분류는 단일 테이블(kind로 구분)의 동일 구조 데이터이며 규칙이 완전히 같다:
  - 추가: 이름·색 지정. (kind, name) 유니크
  - 이름 변경: 그 값을 쓰던 태스크의 값도 함께 변경(참조 유지)
  - 삭제: 그 값을 쓰던 태스크는 남은 첫 항목으로 이관. 마지막 하나는 삭제 불가
  - 순서: 드래그 변경. 진행상황 순서 = 보드 열 순서, 우선순위 순서 = 정렬 기준(위가 높음)
- 태스크 모달 안에서의 분류 추가/삭제 기능은 두지 않는다. 관리 창구는 설정 화면 한 곳

### 4.5 진행상황의 done 플래그

- 코드가 '완료'라는 이름에 의존하지 않도록 각 진행상황에 done 플래그를 둔다. 아래 기능이 전부 이 플래그를 기준으로 동작:

| 기능 | 동작 |
|------|------|
| 진척률 | done 상태면 체크리스트와 무관하게 100% |
| 완료 숨김 | done 상태를 감춘다 |
| 보관 | done 상태만 보관 대상 |
| 반복 생성 | done 아님 → done으로 전환되는 순간 다음 회차 생성 |
| AI 브리핑(today_brief) | done이 아닌 것만 포함 |
| 마감일 표시 | done이면 지연/D-day 대신 회색 처리 |

- done 상태가 하나도 남지 않게 되는 변경(플래그 해제·항목 삭제)은 거부한다

### 4.6 반복 태스크

- 반복 주기: 없음 / 매일(1) / 매주(7) / 2주(14) / 4주(28) — 일수 값으로 저장
- 태스크가 done으로 "전환되는 순간"에만 다음 회차 1건을 자동 생성(미리 만들어 두지 않음).
  이미 done인 태스크를 재수정해도 회차가 늘지 않는다
- 다음 회차 생성 규칙:

| 항목 | 규칙 |
|------|------|
| 마감일 | 직전 마감일 + 주기. 결과가 과거이면 오늘을 넘길 때까지 주기를 더한다 (주기 격자 유지) |
| 시작일 | 시작~마감 간격 그대로 유지 |
| 제목·유형·분류·우선순위·메모·반복주기 | 그대로 복사 |
| 체크리스트 | 항목을 템플릿처럼 복사하되 전부 미체크 |
| 상태 | 항상 첫 번째(시작 전) 상태 |

- 예: 7/17 마감·2주 주기를 7/28에 완료 → 다음 마감 7/31
- 월 단위 반복(매월 1일 등 달력 기준)은 지원하지 않는다
- 목록·보드에 반복 배지 표시

### 4.7 진척률 계산

- 요약 뷰의 진척률은 체크리스트를 반영한 태스크별 진척도의 평균:

| 태스크 상태 | 진척도 |
|-------------|--------|
| done | 1.0 (미체크 항목이 남아 있어도) |
| done 아님 + 체크리스트 있음 | 체크된 항목 수 / 전체 항목 수 |
| done 아님 + 체크리스트 없음 | 0 |

- "진행 중이니 0.5" 같은 근거 없는 가중치는 넣지 않는다. 체크리스트 미사용 시 완료율과 동일한 값이 나온다

### 4.8 완료 태스크 보관

- 기준일 이전에 "마감된" done 태스크만 일괄 보관 (완료 시각을 저장하지 않으므로 마감일을 완료 시점의 근사치로 사용)
- 미완료 태스크는 아무리 오래됐어도 보관 대상 아님
- 보관분은 목록·보드·캘린더·타임라인·요약 통계·AI 브리핑에서 전부 제외
- 삭제가 아닌 플래그 처리로 개별 복원 가능, 별도로 영구 삭제 제공
- 실행 전 대상 건수 미리보기(dry-run) 필수

### 초기 데이터(시드)
- DB 파일이 새로 생성될 때 1회만 투입 (태스크를 전부 지워도 재생성하지 않음):
  - 업무유형 7종: 개발, 기획·문서, 운영, 학습, 회의, 투자, 개인 (각 색상 지정)

  - 우선순위 3종: High, Medium, Low
  - 업무분류 8종 기본값 (각 색상 지정)
  - 예시 태스크 15건 + 예시 체크리스트


## 6. API 명세 (REST)

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | /api/meta | 설정 항목 4종 전체(이름·색상·순서·done) |
| POST | /api/options/:kind | 설정 항목 추가 (kind = type/status/priority/category) |
| PATCH | /api/options/:id | 이름·색상·done 수정 (이름 변경 시 태스크 참조도 함께 이동) |
| PATCH | /api/options/:kind/order | 순서 변경 |
| DELETE | /api/options/:id | 삭제 (사용 중이던 태스크는 남은 첫 항목으로 이관) |
| GET | /api/tasks | 전체 태스크(마감일 순), 각 태스크에 subtasks 배열 포함. ?archived=1이면 보관분만 |
| GET | /api/archivable?before=날짜 | 보관 대상 건수 미리보기 |
| POST | /api/tasks/archive | { before } 이전 마감 완료분 일괄 보관 |
| POST | /api/tasks | 태스크 생성 |
| PATCH | /api/tasks/:id | 부분 수정 (모달 저장·드래그 상태 변경 공용) |
| DELETE | /api/tasks/:id | 삭제 |
| POST | /api/tasks/:id/subtasks | 체크리스트 항목 추가 |
| PATCH | /api/subtasks/:id | 항목 수정 (title / done) |
| PATCH | /api/tasks/:id/subtasks/order | 순서 변경. { ids: [...] }에 해당 태스크 전체 항목 id를 원하는 순서로 |
| DELETE | /api/subtasks/:id | 항목 삭제 |

- 성능: /api/tasks는 태스크별 개별 조회 없이 체크리스트를 한 번에 읽어 묶는다(N+1 금지)
- 복원·영구삭제는 태스크 PATCH(archived=0)·DELETE로 처리


## 7. AI 연동 (MCP 서버)

AI 코딩 도구(Claude Code)가 stdio 방식 MCP 서버를 통해 동일 DB를 직접 조작한다.

| 도구 | 설명 |
|------|------|
| list_tasks | 조회. status·type·priority·category·q(검색)·due_before·overdue·archived 필터, subtasks 포함 |
| create_task | 생성. title만 필수, 나머지 기본값(오늘 시작·7일 뒤 마감). parent_id로 하위 생성 가능 |
| update_task | 부분 수정. parent_id로 상위 연결·해제(null) |
| delete_task | 삭제 |
| add_subtask / update_subtask / delete_subtask | 체크리스트 항목 관리 |
| list_categories | 분류별 태스크 수 |
| today_brief | 오늘 기준 브리핑 — 미완료를 지연/오늘 마감/예정으로 분류해 반환 |
| archive_tasks | before_days(기본 30) 이전 완료분 보관. dry_run으로 건수만 확인 가능 |
| restore_task | 보관 복원 |

세부 규칙:
- overdue: true는 "마감 지남 + 미완료"만 반환. 완료된 지난 태스크 제외
- today_brief: days(기본 7)로 예정 구간, category로 범위 축소. 각 항목은 판단에 필요한 필드만
  (제목·분류·우선순위·마감·진행률) + late_days/d_day. 기간 밖 미완료는 summary.later 건수로만
- create_task/update_task에 존재하지 않는 분류명을 주면 분류를 자동 생성
- 도구 파라미터의 enum(상태·유형 등)은 서버 기동 시점 설정으로 고정. 설정 변경 시 MCP 서버 재시작 필요(웹은 즉시 반영)
- 웹 서버와 DB 파일 공유: WAL 저널 모드 + busy_timeout으로 동시 접근 허용
- 환경변수로 DB 경로 변경 가능


## 8. 비기능 요구사항

- 단일 사용자·로컬 실행. 인증/권한 없음
- 프론트엔드는 빌드 단계 없이 정적 파일로 서빙 가능한 구조 권장 (현행: 바닐라 JS)
- 서버 의존성 최소화 (현행: Express 1개. 새 환경의 스택은 자유이되 같은 수준의 단순함 유지)
- 포트는 환경변수로 변경 가능 (기본 4000)
- 자동 테스트: REST API 회귀 테스트, MCP stdio 왕복 테스트, 진척률 계산 단위 테스트 제공
- DB 초기화 = 데이터 디렉토리 삭제 후 재실행

### A.12 페이지 골격 (참고)

각 뷰 페이지는 동일 골격을 공유한다:
`.app(100vh flex)` > `aside(사이드바)` + `main` > `header` + `#viewport`, 그리고 별도 `#modal-root`.
body의 data-view 속성으로 현재 뷰를 구분하며, 내비·사이드바·헤더는 공용 스크립트가 렌더링한다.
